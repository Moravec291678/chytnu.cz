# Account deletion lifecycle

Settings offers the cloud account export before a separate, irreversible account deletion. The user types `SMAZAT` and reauthenticates with Firebase password credentials or Google account selection. The server accepts only a recently authenticated Firebase ID token, derives the UID from that token, and rejects client-supplied owner identities.

`POST /api/account/delete` creates an owner-specific `accountDeletions/{uid}` marker before any removal. Firestore rules deny all owner data access once this marker exists, including delayed writes from an offline or old client. Server photo and progression endpoints also reject marked accounts. The request then advances a leased, retryable workflow; the protected cleanup cron resumes unfinished work after the Firebase Auth account has been removed. The client clears only the current local profile scope and signs out after the server confirms the deletion marker.

The server first revokes sessions. It enumerates every synced Catch, including missing parent documents with orphan photo subcollections, and queues its photo documents and legacy photo references through the existing `photoDeletionJobs` service. It recursively removes all owner subcollections except the photo jobs, including catches/photos, trips, waters, notifications, push subscriptions, sync receipts, and progression state/events. It deletes the two owner-specific rate-limit documents, the user root, and finally the Firebase Auth user. Cloudinary deletion remains in the shared worker, which checks references and ownership again before destruction. Pending and failed jobs remain visible as unfinished work; the account state is `cleanup-pending` or `partial-failure`, never `completed` until all jobs confirm deletion.

The account marker contains only UID, phase, timestamps, cursor, attempts, lease and short error code. Once the Auth user has been removed, the marker is pruned 29 days after the request, including when photo cleanup is still pending. Photo jobs continue independently and retain the owner/photo identity needed for retry or operator diagnosis. Confirmed photo job receipts follow the separate photo cleanup retention policy. Unfinished photo jobs must not be pruned while a Cloudinary asset may still exist.

Production requires the protected `/api/cloudinary/cleanup` cron with `CRON_SECRET` and the Firestore rules and indexes in this repository. No deployment or production account deletion is part of this stage. Tests use fakes and Firebase emulators only. A controlled dedicated test account and a physical iPhone remain manual verification gates.
