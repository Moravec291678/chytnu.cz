# Cloud photo deletion lifecycle

Removing a photo from the active Catch remains local-first. The existing Catch repository immediately removes it from the active record and queues a durable `photo-delete` operation. After the owning Catch/photo metadata has been tombstoned in Firestore, the authenticated `/api/cloudinary/delete` request creates an idempotent owner-scoped job at `users/{uid}/photoDeletionJobs/{stableJobId}`. The server derives its Cloudinary public ID; the browser never supplies one. The job's `deleteAfter` is server `requestedAt + 1h`, leaving time for a previously signed upload to finish or expire before the first safe daily sweep. Catch deletion tombstones its photo documents as part of the existing Firestore sync transaction. For legacy Catch records with embedded `photos` and no photo subdocuments, the same transaction creates owner-scoped child tombstones from the embedded metadata; the rules permit this only during deletion of a Catch that already had an embedded photo list.

`/api/cloudinary/cleanup` is a server-only worker and recovery sweep. It requires `Authorization: Bearer <CRON_SECRET>`. It backfills a missing server job from owner-scoped Firestore photo tombstones and processes due jobs with a lease. Job states are `pending` (waiting for `deleteAfter`), `deleting` (leased worker attempt), `retry` (provider error with a due time), `deleted` (provider confirmed), `blocked-reference` (photo or active Catch still references the asset), and `permanent-failure` (invalid job identity). A stale `deleting` lease can be claimed again. Before calling Cloudinary, the worker checks current photo metadata and the active Catch's photo references, including legacy reference formats, and verifies the stored public ID against the owner/Catch/photo identity. A confirmed deletion (including `not found`) records confirmation on the photo tombstone. A confirmed tombstone cannot create another job. Completed job receipts and confirmed photo tombstones are selected for pruning 29 days after server confirmation, leaving one day for the daily sweep before the 30-day retention target. Pending, retry, and blocked jobs are unfinished work, not completed receipts; they remain until an operator resolves them so the asset is not forgotten. Cron failures can delay pruning, so a strict wall-clock maximum requires operational monitoring or a more frequent scheduler.

Deletion jobs contain only owner/Catch/photo IDs, the server-derived Cloudinary ID, timestamps, status, attempt count, and a short error code. They contain no photo bytes, Catch notes, GPS, tokens, or credentials. Photo tombstones retain existing Firestore photo metadata until the provider confirms removal. Confirmation atomically compacts each tombstone to photo ID, deletion flag, original deletion time, and server confirmation time; the later sweep removes it. The separate `syncOperations`, `syncChanges`, and Catch/Trip/Water tombstones belong to the general sync protocol and cannot safely be deleted on this 30-day photo schedule without a stale-client/full-resync migration.

Account deletion uses the same `enqueue({ ownerId, catchId, photoId })` service for every photo identity enumerated by the server from Catch photo documents and legacy embedded references. It blocks new account writes before queuing, retains the jobs after removing Catch records and Firebase Auth, and waits for the shared worker to confirm each asset. The worker derives the public ID, checks owner scope, and accepts an absent asset as complete.

`vercel.json` currently schedules this route daily at 00:00 UTC. Configure a random `CRON_SECRET` of at least 16 characters in the Vercel project before deploying this change; without it the route deliberately returns an error and no scheduled cleanup occurs. The endpoint can also be called by a trusted external scheduler with the same bearer secret. Never put that secret in the browser or a public workflow file. Keep the existing Vercel daily schedule as a fallback if an external scheduler is added.

The one-hour `deleteAfter` safety window plus a daily worker makes a healthy asset eligible at the first daily sweep, normally about 1–25 hours after the server job is created. Transient-error retries run on later daily invocations. The app may take additional time to sync a deletion while offline, so timing starts when the server job is created, not when the user taps Delete offline. Cron scheduling, upload completion, and Cloudinary availability prevent a strict 24-hour guarantee.

Cloudinary `destroy` returning `not found` or rejecting with HTTP 404 confirms cleanup and stops retries. Other provider failures retain the job with exponential backoff from 5 minutes to 12 hours; the scheduler never bypasses `nextAttemptAt`, and the browser does not poll this queue.

The general Firestore sync operation receipts and entity tombstones remain owned by the sync protocol. They are not pruned by this photo sweep: deleting those records without a cursor-expiration/full-resync protocol could let a device offline for more than 30 days replay an old delete or resurrect stale data. That separate sync-retention change is still required if the 30-day limit is intended to apply to every sync receipt, rather than the photo deletion tombstones in this lifecycle.
