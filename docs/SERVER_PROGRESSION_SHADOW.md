# Server progression shadow calculator

`POST /api/progression/claim-catch` is an authenticated, opt-in shadow endpoint. Set the server-only `SERVER_PROGRESSION_SHADOW=true` flag to enable it; without the flag it returns 503. The request accepts exactly `{ "catchId": "…" }`. It ignores client XP, levels, reward IDs, and evidence supplied in the request.

The endpoint reads the caller's Catch, related Trip/Water and prior server shadow records from `users/{uid}/…`. Firestore transactions write stable per-Catch reward event IDs, an owner-scoped photo hash claim, a daily LIMITED cap, and an evaluation state. Event timestamps use Firestore `serverTimestamp()`. The Firestore client rules permit the owner to read events/state and deny all client writes.

`POST /api/progression/reconcile` accepts exactly the authenticated device's observed local XP total and an aggregate of its locally calculated Catch XP for Catch IDs already in that device's server-claim queue. It does not accept client-authored reward events or XP awards. The server reads and sums its own unique event documents, stores a monotonic `legacyBaselineXp` in `users/{uid}/serverProgressionState/summary`, and returns `legacyBaselineXp + serverEventXp`. The UI overlays this shared online total; when offline or the shadow endpoint is disabled, it continues to use the local ledger. Repeated requests and a lower-XP device cannot reduce the stored baseline or duplicate an event reward.

The baseline is a compatibility bridge for XP earned before server claims existed. Since that history only exists in the user's local ledger, the first report of previously unseen legacy XP cannot be independently proven by the server. New Catch XP is excluded from the baseline when its stable Catch ID is in the server claim queue; the server event total becomes authoritative after claim confirmation. Keep this limitation explicit until a trusted migration source exists.

The server only treats a photograph as available after Firestore metadata points to its expected owner/Catch/photo Cloudinary object and reports `synced` with a syntactically valid SHA-256. Existing upload verification checks Cloudinary object presence, size, and format, but does not independently download and hash the bytes. EXIF and GPS stored in the Catch are client-provided evidence: the calculator checks plausibility and consistency, but does not claim they are tamper-proof.
